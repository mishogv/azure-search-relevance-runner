2. Where I agree with the brief, and where I would differ

Agree. The three mechanisms are real and the order is right: fix query construction first (deployable alone, one-line rollback), then the index. SearchMode.Any turns every two-word query into an OR, and the regex wrapper is structurally incapable of matching identifiers: Azure matches /.*x.*/ against single lower-cased tokens, and | is not an operator in its Lucene syntax. Dropping the wrapper is a pure win, not a trade-off (regex queries also bypass BM25 scoring).

Differ or add — each point verified on the service, not assumed:

  1. The "In current result" column is not what the code does. 222 rows deviate, in a handful of explainable groups: 98 regression-guard rows marked "not found" are found today (bare type codes such as PRT return 100+ records; O10099.nc returns every .nc file); 65 "noise" rows marked "found" cannot be found on one field (steel plate shares no token with its target); 16 rows marked "currently works" need normalization that does not exist yet (BAT10172119); and the failure on quoted input is HTTP 400 "Failed to parse regex expression", not 500. I would treat the sheet as the target contract, not as a baseline, and re-baseline together before Step 2 lands.
  2. Underscore and dotted digits do not split. Analyze API output: 000_081_835 → one token, DOC.1009.2063.19 → doc + 1009.2063.19, abcd.pdf and TURBINE.H → one token each, O10043.nc → o10043 + nc. That is the precise reason normalized identifiers cannot be fixed query-side, and why extension false positives only affect letter-digit filenames.
  3. Sub-fields do not exist. content/exact is not valid; the design uses three top-level fields fed from the same string. The prefix field indexes edge n-grams but is searched with the plain normalized analyzer, otherwise 000-081 would itself be n-grammed and match everything starting with 00.
  4. Normalize everything that is not a letter or digit, not only - _ . and space: 113 documents end with zero-width spaces (U+200B) and NC-4421-B_2#10.H must match NC4421B210H. A keyword-tokenized field keeps U+200B inside the token, so the char filter strips it; the query encoder strips it too (six queries carry it inside the quotes).
  5. Edge n-gram minimum 4, not 2, and bare type codes are exact-match only. The shortest prefix case is ITM7; 78 regression-guard rows require RCP, DOC, PRT to return nothing. A single alphabetic token of three letters or fewer therefore queries only the exact field.
  6. Escape set. Full Lucene syntax needs + - & | ! ( ) { } [ ] ^ " ~ * ? : \ /; the current code misses - * ? { } and / (which opens a regex — one regression-guard query, M-486300-1/4, contains it). A leading - or ! is a NOT and single negations are rejected, so those are escaped at term start. No case uses wildcards; I propose escaping * and ? until a case says otherwise.

3. Plan

Step 1 — baseline and plan. Done (this document, the runner, per-row results, the deviation groups above).

Step 2 — query side. Extract mode resolution into a pure function (no behaviour change, tests green) → default SearchMode.All → rewrite EncodeSpecialCharacters by a decision table: empty → *; strip U+200B; balanced quotes → phrase kept, inner specials escaped; unbalanced → quotes removed; plain text → specials escaped, no regex, no wrapper; the OR/AND keyword detection stays. Each commit is independently deployable. Measured on the sheet: all 98 Must-Suppress rows pass, all 43 quoted identifiers pass, no request errors; the Step-2 rows that remain are ABRASIVE-DISC 115 (needs infix matching, see §5) and the lone " query.

Step 3 — index side. Three analyzers — identifier_exact (keyword, lowercase, trim), identifier_normalized (letters and digits only), identifier_prefix (normalized + edge n-grams 4–30, index side only) — on fields content_exact, content_norm, content_prefix, with a scoring profile exact 10 / normalized 5 / prefix 2 / standard 1. The query becomes fielded: a single token queries exact OR normalized OR prefix OR the standard field; several tokens query the whole input exactly and normalized, each identifier-like token exactly and normalized, OR all terms on the standard field. That rule is what lets 91260A27A04-01-00 seal ring still find its part while ITM-7723 component does not pull in ITM-7723-14.6. Measured: 708 of 710, all four regression tabs green.

Rollout. Analyzer assignment is immutable per field, so production gets the new fields side by side: add analyzers and fields (allowIndexDowntime, seconds of downtime) and back-fill with mergeOrUpload, or build the new index next to the old one and swap with an alias. The query builder switches per endpoint behind a flag; the old field stays until the sheet passes against production data.

4. Testing approach

  • The Excel sheet is the contract. The runner locates columns by header, runs each query with top=100 against the chosen builder and index, asserts on Searchable content only (ordinal, untrimmed — U+200B included), records any rejected request as ERROR, and reports pass/fail by tab, category and To fix in.
  • Every run writes a JSON file; compare a b lists each case whose outcome changed, split into fixed and broken. That is the regression gate between steps and later between the dev and production indexes.
  • Unit tests (xUnit) cover the encoder decision table and mode resolution without Azure; tokenization is checked with the Analyze API, never guessed, and the token tables go into the report.

5. Risks and questions

  1. Baseline authority. The sheet's current-result column was derived, not measured (§2.1). I propose we accept the real baseline as the starting point and keep the sheet as the target; otherwise Step 1 can never be "done".
  2. Bare type codes. The regression guard wants RCP to return nothing; the brief wants nc to return .nc files. Both are 2–3 letter tokens. My rule treats short alphabetic tokens as identifier evidence only; if extension-only search matters to operators, it needs its own rule (a known extension list) — please confirm which behaviour you want.
  3. Infix matching. ABRASIVE-DISC 115 → M-ABRASIVE-DISC 115X1 needs a substring match (115 inside 115X1). The three analyzers in the brief cannot do it; an infix n-gram field can, at an index-size cost. Decide per product.
  4. Lone quote. Two cases expect a specific document for the query ". After stripping the quote the query is * (724 documents); which 100 come back is arbitrary. I suggest asserting "no error" for these rows.
  5. Production shape. The sheet models one field and one index; production has an index per entity type plus a global endpoint, and presumably name/description fields. The fielded query and scoring profile must be applied per index, and the regression sheet must be run against real data before the alias swap.
  6. Where do the zero-width spaces come from? They look like copy-paste artefacts from an ERP or spreadsheet. Stripping them at ingestion is cheaper than carrying them through every analyzer.
